PROBLEM STATEMENT
Lab D's 10 Acer Predator PCs run standalone with no centralised virtual machine repository. Each session requires manual OS installation on individual machines, and with no snapshot or rollback mechanism, a corrupted VM means a full reinstallation — wasting class time and lecturer effort.
RESEARCH QUESTIONS
  1. How can a Dell R440 master node coordinate a centralised image repository distributed as node-local golden templates across 10 Acer Predator edge nodes (lab-d-cluster) simultaneously?
  2. What thin-provisioning and snapshot strategy minimises storage consumption while supporting rapid VM rollback?
  3. What are the minimum VM specifications (RAM, vCPU, disk) needed for each course type to function adequately on Acer hardware?
SCOPE & TASKS
  1. 01Install and configure Proxmox VE across the Dell R440 master node and the 10 Acer Predator edge nodes (lab-d-cluster); partition storage for image repository vs running VMs.
  2. 02Create 7 golden VM images: Ubuntu Server 22.04, Windows Server 2022 + AD, DVWA, Kali Linux 2024, OPNsense, Docker Host, Windows 10 workstation.
  3. 03Implement thin provisioning (Proxmox linked clones) and automated daily snapshot strategy; expose node-local golden templates for FYP-1C's Terraform automation to clone from.
  4. 04Document image creation SOP and produce capacity planning report (max concurrent VMs given RAM/storage) — validated in practice at roughly 6 concurrent student VMs per Acer node with a 3-deployment-per-student cap.
  5. 05Build and test backup/restore automation scripts; measure boot time benchmarks per image type.
METHODOLOGY
Action Research Benchmarking Iterative Build Documentation
Build-test-document cycle. Each VM image is built, snapshot tested, stress-tested for boot time, and documented before being considered production-ready. Capacity planning uses empirical RAM/CPU measurements under load.
