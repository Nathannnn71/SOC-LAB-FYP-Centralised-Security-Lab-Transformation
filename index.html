University Security Operations Lab · FYP January - Auguest2026

Building a
SOC Lab
from Scratch

A phased, student-driven transformation of a physical computer lab into a fully virtualised, centrally managed Security Operations Centre training environment — built on existing hardware with zero commercial licensing cost where possible.

9 FYP candidates · 2 semesters · 3 phases
Each candidate owns one functional layer. Together they form one coherent system.

⚠ PROBLEM STATEMENT

The lab currently runs 20 standalone Acer Predator PCs connected through pfSense with no centralised management, no monitoring, and no repeatable lab deployment. Each session requires manual setup. Security exercises (Red/Blue Team) cannot be conducted safely or at scale. New Lenovo PCs arriving as tech refresh create an opportunity to restructure entirely.

✓ PROPOSED SOLUTION

Virtualise the 20 Acer PCs as edge hypervisors (Proxmox) managed by a Dell R440 master node. Deploy 6 student FYP projects across 2 semesters to build — layer by layer — a complete virtualised SOC training platform covering image management, network segmentation, automation, monitoring, attack/defence labs, IDS/IPS, honeypots and a self-service orchestration portal.

PROBLEM STATEMENT
All 20 Acer PCs currently share a flat network with no isolation. A student on any PC can reach any other PC. Vulnerable VMs (DVWA, unpatched Windows) are directly reachable from the university network. There is no mechanism to safely run Red vs Blue exercises without risk of actual network harm.
RESEARCH QUESTIONS
  1. How can a 6-VLAN architecture on a single managed switch provide full isolation between management, student, red-team, blue-team, honeypot and monitoring traffic?
  2. What is the safest and least disruptive migration path from pfSense to OPNsense without service downtime?
  3. Can inter-VLAN firewall rules be enforced strictly enough to prevent Red Team traffic from escaping VLAN 30?
SCOPE & TASKS
  1. 01Design complete 6-VLAN architecture: V10 Management, V20 Student VMs, V30 Red Team, V40 Blue Team, V50 Isolated (malware), V60 Monitoring.
  2. 02Document all existing pfSense rules; deploy OPNsense in parallel; replicate all rules; test cutover procedure.
  3. 03Configure managed switch with 802.1Q VLAN tagging; assign Acer Proxmox nodes to correct VLANs.
  4. 04Implement inter-VLAN routing policies — deny Red Team (V30) from escaping to Management (V10) or university uplink.
  5. 05Produce network isolation test report proving each VLAN boundary holds under penetration attempt.
METHODOLOGY
Network Design Parallel Migration Penetration Testing (isolation)

  5. 05Privilege Escalation — Linux SUID exploit chain and Windows token impersonation; post-exploitation data gathering.
  6. 06Lateral Movement — Pass-the-Hash / Pass-the-Ticket in AD environment; pivot across Acer nodes via Meterpreter routing.
  7. 07Automated Reset — Ansible playbook to snapshot-rollback all target VMs to clean state after each lab session.
